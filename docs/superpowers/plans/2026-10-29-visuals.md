# Visuals (Stage 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the modular Ball Studio its visual modules: shader materials on things and picture effects on Scene defaults, styled looks (shapes, fills, outlines, glow, rainbow, stretch), streak trails and hit-burst particles, all as library modules in the Shader, Look, Trail and Particles slots, drawn by new passes in `bpe-gfx`.

**Architecture:** `bpe-gfx` grows four render passes behind one seam, the `Frame` lists: styled balls (`looks`), trails (`trails`), particle bursts (`bursts`) and an effect chain (`effects`) that runs hand-written WGSL effects over the HDR picture in two stages (Things, before flashes and particles; Picture, after). An "object picture" (local xy, thing code, cover) lets an effect paint only one thing. A new `ModuleDraw` plugin lets a module draw for every thing whose slot resolves to it, so Shader, Trail and Particles modules draw themselves and new thing kinds (stages 3, 6, 7) get them for free. `bpe-runtime` records a short position history for things that wear a trail. `bpe-kit` adds one folder per module kind (`modules/shader`, `modules/trail`, `modules/particles`, `modules/look/styled.rs`); the shader kinds are generated from the effect files' comment headers, which keep the old `fn effect(uv, p)` contract so stage 4's graph compiler can target the same chain.

**Tech Stack:** Rust 2024, wgpu 30, egui/eframe 0.37 (egui_kittest), glam 0.34, bytemuck, naga 30 (dev-dependency, validates the built-in effects in tests).

**Spec:** `docs/superpowers/specs/2026-10-29-modular-studio-design.md` (sections 2 "Things", 3 "Slots and modules", 5 "Engine", 8 "Testing"). Port sources, read-only: `crates/bpe-render/src/effects/{mod.rs,chain.rs,prelude.wgsl,builtin/*.wgsl,templates.rs}`, `crates/bpe-render/src/{particles.rs,frame.rs,lib.rs}`, `crates/bpe-render/src/shaders/{ball_look.wgsl,scene.wgsl,gpu/particles.wgsl,gpu/common.wgsl}`, `crates/bpe-scene/src/{ball_style.rs,particles.rs,effect.rs}`.

## Global Constraints

- Old crates (`bpe-scene`, `bpe-sim`, `bpe-render`, `bpe-audio`, `bpe-export`, `bpe-music`, `bpe-graph`) are never edited. `bpe-graph` stays untouched (stage 4 owns Nodes).
- `BTreeMap`/`BTreeSet` everywhere; never `HashMap`.
- Changes to shared files stay small and additive (stages 3, 4, 6, 7 run in parallel on `main`): new folders under `crates/bpe-kit/src/modules`, new files under `crates/bpe-gfx/src`, a few lines in `frame.rs`, `lib.rs`, `world.rs`, `balls/draw.rs`, `balls/mod.rs`, `balls/sim.rs`, `arena/draw.rs`, `inspector.rs`, `scenes.rs`. Rebase on `main` before merging.
- The editor stays `ball-studio-next.exe`; the old `ball-studio.exe` is not replaced (stage 8).
- Settings contract (`bpe_core::check_registry`): at most `MAX_SIMPLE = 6` Simple settings per kind; `keyframe`/`pulse` only on Number, Int, Vec2 or Color settings; every key unique.
- WGSL: never name a field or variable `target`, `active` or `move` (reserved; silently breaks compilation on some drivers). At most 8 storage buffers per shader stage (default wgpu limits).
- Every egui control gets `.labelled_by(label.id)` or a `WidgetInfo` name so kittest can find it; pickers are `menu_button`s; `ui.set_min_width(ui.available_width())` first in side panels.
- `cargo fmt --all`, `cargo clippy --workspace -- -D warnings` and `cargo test --workspace` pass before every commit that touches Rust. Workspace tests take about 10 minutes; run them in the background. Environment: `apt-get install libasound2-dev mesa-vulkan-drivers libxkbcommon-x11-0 libxkbcommon0 mingw-w64 xvfb xdotool imagemagick`, `rustup target add x86_64-pc-windows-gnu`.
- Picture tests run on the software GPU through `bpe_gfx::headless_device()` and skip (print and return) when there is no adapter; `BPE_SAVE_RENDERS=1` saves PNGs under `target/pictures`.
- Golden logs: `crates/bpe-kit/tests/golden.txt` (release) and `golden-debug.txt`; rewrite with `BLESS_GOLDEN=1` only when physics is meant to change (it never is in this stage).
- Commit messages are plain sentences ("Draw trails behind balls"); no model names in commits, PR or code.

## Review Focus

1. A shader whose WGSL fails to compile (a future custom effect, a driver quirk) must not crash the editor: the effect is skipped, the rest of the picture still draws and the status line says why. Test `a_broken_effect_is_skipped_and_reported` (Task 4).
2. Scrubbing backwards with Echo on must not smear the old future into the past: the echo history restarts after a time jump above 0.25 s. Test `echo_builds_up_and_restarts_after_a_seek` (Task 4).
3. Ten thousand balls landing at once must not overflow the particle buffers or stall: at most 400 bursts and 200,000 live particles, newest first, no panic. Test `the_particle_budget_keeps_the_newest_bursts` (Task 11).
4. A thing whose body count grows (stage 6 emitters) or a body index beyond the recorded history must draw what exists and never panic. Test `history_grows_with_the_bodies_and_answers_nothing_for_unknown_ones` (Task 9).
5. Visual modules never change the physics: each stage 5 scene is a stage 2 scene plus visuals and keeps that scene's exact event log; adding a trail rebuilds playback but replays identically; a Shader module at `blend` 0 leaves the picture bit-identical. Tests `stage5_scenes_keep_their_stage2_twins_logs` (Task 14), `a_trail_changes_the_fingerprint_but_not_the_log` (Task 9), `blend_zero_leaves_the_picture_unchanged` (Task 4).

Thing codes: a thing is `code = id.0 as f32 + 1.0` in the object picture's third channel, plus `seed * 0.5` (seed in [0, 1)) for balls, so `floor(code) - 1` is the thing and `fract(code) * 2` the seed. 0 means nothing. An effect's `apply_to` is 0 for the whole picture or the thing's code.

  - `#[derive(Clone, Copy, Debug, PartialEq, Eq)] pub enum Stage { Things, Picture }`.
  - `#[derive(Clone, Debug, PartialEq)] pub struct EffectCall { pub key: u64, pub wgsl: std::borrow::Cow<'static, str>, pub params: [f32; 16], pub blend: f32, pub apply_to: f32, pub stage: Stage }`.

### Task 4: The effect chain and the object picture

**Files:**
- Create: `crates/bpe-gfx/src/effects/chain.rs`, `crates/bpe-gfx/src/shaders/object.wgsl`
- Modify: `crates/bpe-gfx/src/lib.rs` (Targets keep the HDR texture with `COPY_SRC | COPY_DST | TEXTURE_BINDING | RENDER_ATTACHMENT`; an `object` Rgba32Float texture with `RENDER_ATTACHMENT | TEXTURE_BINDING`; object pipelines; chain runs; `shader_problems()`), `crates/bpe-gfx/src/shaders/scene.wgsl` only if the ball or shape vertex outputs lack what `object.wgsl` needs (local position, radius); prefer adding to `object.wgsl`.
- Test: `crates/bpe-gfx/src/effects/chain.rs` unit tests (GPU, skip without an adapter)

**Interfaces:**
- Produces:
